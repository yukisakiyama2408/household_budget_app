# パフォーマンス調査・改善記録（2026年11月6日）

対象は現在のNext.js 16.2.4アプリ。調査開始時のコードは `18e59a8` と同じ実装で、README・画面構成の再開メモには既存の未コミット変更があった。それらの内容を維持して実施した。

UIの配置・CSS・表示項目・金額計算・重複判定・登録方式・URL仕様は維持した。DBスキーマの変更、永続キャッシュの導入、実データの更新、デプロイは行っていない。画面構成再編のステップ6〜9は別作業として残っている。

## 調査範囲と計測の限界

- ページ・共通レイアウト・ナビ・認証Proxy、データ取得と集計、Server Actions、CSV入出力、固定費反映、グラフ、通知・Service Worker、画像・フォント、クライアントのイベント・タイマーを確認した。
- 実測：本番ビルドのJavaScript入口ファイル量、ローカルのCSV重複判定CPU時間。
- 検証用の測定：実際の取得関数と年次コンポーネントをテスト用DBに接続し、クエリ数・並列性・返却JSON量・結果の一致を比較。通信は1回8msで模擬した。
- 未計測：認証済みブラウザでのTTFB・LCP・INP、実DBの応答時間・実行計画、モバイル実機、ヒープスナップショット。本番の体感速度の改善率は断定しない。

## 問題点・優先順位

「高」はデータ量が増えたときや該当画面での影響が大きいという評価で、実ユーザーの待ち時間を計測して順位付けしたものではない。

| 優先度 | 影響 | 箇所・問題 | 確認方法 | 対応 |
| --- | --- | --- | --- | --- |
| P1 | 高 | CSVの各行について既存取引を毎回全走査し、編集・絞り込み中にも繰り返す | コード・ローカルCPU計測 | 日付＋金額の索引と店舗Setで検索。索引・絞り込み・件数をメモ化 |
| P1 | 高 | 日次表示の独立した4種類の取得が逐次実行 | テスト用DBで同時実行数を記録 | 並列化。履歴・精算の取得列も必要な項目に限定 |
| P1 | 高 | 年次画面がサマリーと推移を別取得し、同じ年の取引・相殺情報を重複取得 | テスト用DB・実コンポーネント | 推移1回からサマリーを算出。表示結果のハッシュ一致を確認 |
| P1 | 高 | 残高表示で全履歴の内容・店舗など計算に使わない列も取得 | クエリ確認・模擬JSON量 | 金額・収支区分・支払方法、引落金額だけに限定 |

| P2 | 中 | 全画面共通のナビが改善要望候補などの取得を待つ | コード、実通信時間は未計測 | 未対応。遅延取得・表示境界の導入は初回操作の待ち方も含めて検討する |

| P2 | 中 | 固定費適用が1件につき取引・適用ログの2回書き込み | コード | 未対応。バッチ化は重複防止・途中失敗・原子性の設計が必要 |

| P3 | 低 | コピー完了表示などの短いタイマーに一部cleanupがない | コード | 未対応。有限のタイマーであり、持続的なメモリリークとは断定しない |
| P3 | 低 | CSVの直近取引取得がフォーム切り替え後にも完了する可能性 | コード | 初期Effectのcleanupで古い結果の状態反映を抑止。通信自体のキャンセルではない |

`getMonthlySummary` など一部の集計クエリやCSVの重複候補取得には全件ページングがなく、DB側の返却上限によっては対象が切れる可能性もある。これは実DBの設定と結果を確認してから修正する必要があり、今回の高速化では上限・集計仕様を変更していない。

DBの実インデックスは確認できていない。リポジトリのmigrationに定義がないことだけで、稼働DBにインデックスがないとは判断しない。次段階では認証済みの検証環境で `EXPLAIN` とインデックス定義を確認し、取引の `(date, created_at, id)` などの複合インデックスの必要性を評価する。

既存の良い点：取引一覧はキーによる50件単位の取得、検索には日本語変換を考慮した待機、主なイベントリスナー・検索タイマー・日次タイマーにはcleanupがある。Rechartsは分析で使用され、Excel用の `xlsx` はCLIスクリプト側で使用されている。これらを理由なく置き換えていない。Service Workerは主に通知用で、アプリ全体のキャッシュを無制限に増やす処理は見当たらなかった。

## 改善前後の結果

### CSV重複判定：ローカルCPU実測

既存取引10,000件、入力2,000行。各実装を9回実行した中央値。改善後には索引構築時間も含む。判定配列のSHA-256は一致した。

| 項目 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 1回の判定処理 | 209.243ms | 1.950ms |

これはNode上の固定データでの計測であり、ブラウザでのCSV処理全体やアップロード・登録速度の計測ではない。索引はメモリを使うが、既存取引が変わるまで再利用し、各行ごとの一時的な全件配列生成を避ける。

### 取得処理：模擬DBでの比較

取引180件と精算2件の同一データを使用し、日次・残高・年次表示結果のSHA-256が修正前後で一致した。

| 項目 | 改善前 | 改善後 | 解釈 |
| --- | ---: | ---: | --- |
| 日次のクエリ数 | 4 | 4 | 件数は同じ |
| 日次の最大同時取得数 | 1 | 4 | 独立した取得を並列化 |
| 日次の模擬時間・中央値7回 | 36.730ms | 9.351ms | 各通信8msのテスト条件。本番速度ではない |
| 日次の返却JSON量 | 113,189B | 11,973B | このfixtureにおける取得列削減の結果 |
| 残高の返却JSON量 | 113,187B | 9,529B | 同上。クエリ数は2のまま |
| 年次画面のクエリ数 | 4 | 2 | 重複した取得を除去 |
| 年次の模擬時間 | 9.822ms | 9.626ms | 元々並列であり、時間差の有意性は主張しない |

### 本番ビルドの入口JavaScript

`page_client-reference-manifest.js` の `entryJSFiles` をルートごとに重複排除し、各JSを個別gzipした合計。フォント・CSS・画像・RSC通信・必要時の追加チャンクは含まない。ブラウザの実転送量・キャッシュヒット・Lighthouse結果とは異なる。

| ルート | 改善前gzip | 改善後gzip |
| --- | ---: | ---: |
| ホーム | 27,359B | 27,359B |
| 収支 | 31,152B | 31,255B |
| 予算 | 48,251B | 48,251B |
| 分析 | 158,147B | 158,147B |
| 振り返り | 46,173B | 46,173B |
| CSV取り込み | 36,942B | 30,595B |

CSV取り込みは約17.2%削減（36.1→29.9KiB）。収支は再計算抑制のコード追加により103B増加した。CSV解析ライブラリはファイルを読んだ時点で追加取得されるため、取り込み処理全体で転送されるライブラリを除去したわけではない。
